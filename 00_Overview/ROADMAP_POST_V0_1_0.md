## Откладывается на следующий уровень развития

После завершения четырёх этапов выше, при положительной обратной связи с пилотов и достаточном объёме клиентов:

### Подпись установщика (2.1 + 2.2)

**Что:** коммерческий сертификат юридического лица + подпись `.exe` + нотариальное заверение macOS.

**Почему отложено:** для офлайн-программы с маленькой клиентской базой подпись — вопрос удобства, не работоспособности. Текущие способы обхода без подписи:

1. **Portable ZIP вместо установщика** — клиент скачивает архив, распаковывает в свою папку, запускает оттуда. Не триггерит UAC-окно установщика.
2. **Однократный обход SmartScreen вручную** — при первом запуске «Подробнее» → «Выполнить в любом случае». Описано в `Final/PILOT_INSTALLATION_GUIDE.md`.
3. **Накопление SmartScreen Reputation** — через 3–6 месяцев активных скачиваний Microsoft автоматически добавляет издателя в доверенные, предупреждение исчезает.

**Когда вернуться:** при росте клиентской базы выше ~20–30 одновременных установок, когда ручной обход начнёт реально пугать незнакомых пользователей.

### Шифрование базы проектов (2.4)

**Что:** прозрачное шифрование SQLite-базы с ключом, привязанным к учётной записи Windows.

**Почему отложено:** защита данных — задача клиента (физическая безопасность машины + пароль учётной записи). Aurora не хранит регулируемые персональные данные.

**Когда вернуться:** при появлении клиентов из фарма/финансов крупного масштаба, где юристы потребуют шифрование на стороне клиента согласно 152-ФЗ.

### Универсальная резервная копия (2.3)

**Что:** наблюдатель за папкой (OneDrive, Yandex Disk, Dropbox — любая папка по выбору клиента).

**Почему отложено:** клиенты сами руками настраивают копирование базы. Риск потери проекта существует, но решается через прямую инструкцию пользователю.

**Когда вернуться:** после первого случая потери проекта у клиента (или при крупном клиенте с требованием SLA по данным).

### Кросс-платформа (2.6)

**Что:** живая проверка работы на Linux и macOS на серверном автомате.

**Почему отложено:** пока только Windows. Российский рынок офисных машин подавляюще на Windows.

**Когда вернуться:** на отдельном этапе после первой коммерческой стабильности — когда появятся агентства с парком Mac у дизайнеров или клиенты из IT-сектора на Linux.

### ИИ-функции (3.1, 3.2, 3.3)

**Что:** объяснение прогноза через языковую модель, подсказчик бренда-двойника, категорийные шаблоны.

**Почему отложено:** Aurora пока остаётся **офлайн-первой программой**. Облачные ИИ-возможности требуют отдельного архитектурного решения по 152-ФЗ (передача данных к Anthropic / OpenAI / российскому ИИ-поставщику) и согласия клиента.

**Когда вернуться:** отдельный продуктовый этап «Aurora с ИИ-помощниками» — после стабилизации офлайн-выпуска и принятия архитектурного решения.

### Открытый реестр прогнозов (4.1)

**Что:** публикация реальной точности прогнозов через 12 недель после выпуска. Это сильнейший маркетинговый ход — ни Nielsen, ни Kantar этого не делают.

**Почему отложено:** требует накопления данных. Сейчас в системе нет даже одного завершённого прогноза с известным результатом.

**Когда вернуться:** через 6+ месяцев после первого пилота — когда наберётся 10–20 прогнозов с известными исходами. Минимальная версия (сбор данных в базу прямо сейчас с согласия клиента, страница публикации потом) — может быть включена в этап 3 или 4 при желании.

### Веб-проверяльщик подписей (4.2)

**Что:** сервис `verify.auroraai.pro` — любой третий человек может проверить подлинность отчёта без установки программы.

**Почему отложено:** для большинства сделок не критично. Нужно когда появятся клиенты в регулируемых отраслях, где отчёт показывается юристу или аудитору.

**Когда вернуться:** при появлении регулируемых клиентов или при пакете возможностей «прозрачность» (вместе с 4.1 реестром).

## Главные риски плана

1. **Откладывание подписи установщика** — может стать препятствием для конверсии при росте клиентской базы. Метрика для возврата к 2.1 + 2.2: когда более 5 разных людей попросят инструкцию по обходу SmartScreen.

2. **Откладывание шифрования базы (2.4)** — если первый же фарма-клиент потребует — нужно вставлять в план срочно.

3. **Откладывание Linux/macOS (2.6)** — если агентство-партнёр захочет — потребует ~12 часов на проверку + ещё столько же на устранение per-OS багов.

4. **Промежуточные аудиты могут найти настоящие проблемы.** Заложил 10–15 часов на закрытие каждого, но в реальности эта цифра колеблется. Хороший знак — план дисциплинированно использует аудит как часть процесса.

5. **Откладывание ИИ-функций (3.1, 3.2, 3.3)** — конкуренты могут опередить с «AI-powered forecast». Контрход: «у нас прозрачная математика, без чёрного ящика» — позиция работает в фарме и регулируемых отраслях.

## Что делать прямо сейчас (после согласования плана)

Первый блок этапа 1 — **«базовое ядро»** (1.1 + 1.2 + 1.3), 18 часов работы. Без него пилот невозможен.

После этих трёх — короткая проверка работы программы end-to-end на чистой машине, и дальше пункты 1.4–1.8.
