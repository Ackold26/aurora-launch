## 1. BLOCKER findings

### B9 — Schema namespace fragmentation: per-task schemas в YAML vs unified bundle schema в C6 spec

**Где:** все 7 YAMLs `output_bundle_target.schema` field; PHASE_A_REQUIREMENTS C6 Section 6.1.A schema_kinds list.

**Проблема:** YAMLs declare `schema: optimize_v3.0`, `optimize_scenario_v3.0`, `optimize_reach_v3.0`, `launch_v3.0`, `launch_paused_v3.0`, `brand_awareness_v3.0`, `brand_bridge_v3.0` — **7 разных schema identifiers**. Но PHASE_A_REQUIREMENTS C6 spec говорит unified bundle `schema_version="3.0"` для kind `aurora_bundle` (combined Studio + Launch additive fields). Это создаёт **двусмысленность**:
- Какой `schema_version` пишется в bundle's manifest.json: "3.0" (per C6) или "optimize_v3.0" (per YAML)?
- Forward-compatibility check `MIN_APP_FOR_SCHEMA["aurora_bundle"]["3.0"]` — на что mapped?
- Kind `task_spec` в C6 schema_registry list — это для YAML files itself, не для bundle output schema.

**Impact:** bundle composer не знает which schema_version stamp к manifest.json → check_forward_compatibility breaks → Aurora Launch reading Studio bundle получает ambiguous version.

**Fix:** разделить понятия explicitly:
- **`schema_version`** в `manifest.json` = "3.0" (registry-managed, single value across all bundles regardless of task).
- **`bundle_layout_id`** в YAML = task-specific layout description (`optimize_budget_v1`, `launch_proxy_forecast_v1`, etc.) — describes WHICH parquet files + JSON shapes inside, не versions.

Rename YAML field `output_bundle_target.schema` → `output_bundle_target.bundle_layout_id`. Add note к C2 spec Section 2.1.D Bundle composer: «manifest.json combines `schema_version` (registry) + `bundle_layout_id` (task-specific layout)».

### B10 — Invented sources не в C2 adapter list (source taxonomy violation)

**Где:** scenario_what_if YAML (`aurora_optimize_pretrained`, `aurora_econometrica_legacy`), new_brand_forecast YAML (`aurora_econometrica_existing_project`).

**Проблема:** PHASE_A_REQUIREMENTS C2 Section 2.1.A defines 5 source adapters: `dsm_group`, `mediascope_adex`, `mediascope_tv_index`, `digitalbudget`, `custom_xlsx`. Эти 5 = «raw data sources, parsed into canonical schema».

Но в YAMLs я invented:
- `aurora_optimize_pretrained` — это existing `.aurora` bundle output of prior task, не raw data source.
- `aurora_econometrica_legacy` — это legacy `.pickle` v2.0, читается через SchemaRegistry migration, не parsed.
- `aurora_econometrica_existing_project` — это live Эконометрика project bundle.

Это **artifact references** (input-by-reference на existing artifact), концептуально другие vs raw data sources. C2 spec их не покрывает → adapter coverage matrix в C2 incomplete → bundle composer не знает как handle these.

**Impact:** Aurora Launch B0.5+ ProxySelectionStep предусматривает «import .aurora from Studio» button — это use case `aurora_artifact_reference` source. Если C2 spec не предусматривает — Aurora Launch B0.5 hits unspecified source kind → ad-hoc implementation → drift.

**Fix:** ввести **6th source kind `aurora_artifact_reference`** в C2 spec:
```python
class AuroraArtifactReferenceAdapter(SourceAdapter):
    """Reads existing .aurora bundle (pickle inside) — no parsing, schema-versioned."""
    source_id: str = "aurora_artifact_reference"
    # Goes through SchemaRegistry.migrate(...) on read.
```

Update YAML sources to consistent naming:
- `aurora_optimize_pretrained` → `aurora_artifact_reference` (с metadata `referenced_app: aurora_optimize, task: budget_optimization`).
- `aurora_econometrica_legacy` → `aurora_artifact_reference` (с metadata `legacy: true, schema_version: 2.0`).
- `aurora_econometrica_existing_project` → `aurora_artifact_reference` (с metadata `live_project: true, source_app: aurora_econometrica`).

## 2. HIGH findings

### H10 — Source `computed` semantically не source

**Где:** budget_optimization (`seasonality_index`), new_brand_forecast (`category_seasonality_override`), brand_to_sales_bridge (`seasonality_index`).

**Проблема:** `computed` listed as source — но это **derived field generated by Studio engine** (Chow-Lin disaggregation, seasonality decomposition, etc.). User не uploads «computed seasonality», engine derives it. Это конфликтует с definition «source = where user brings data from».

**Fix:** introduce new source kind `derived_internal` в C2 spec для engine-derived fields. Update 3 fields: `sources: [derived_internal, user_input_form]` где user_input_form — opt-in override path.

### H11 — Inconsistent difficulty levels (free-form values, not enum)

**Где:** все 7 YAMLs `ux_hints.difficulty_for_manager` + `difficulty_for_econometrician`.

**Проблема:** observed values:
- Manager: `low`, `medium (proxy selection requires expert judgment)`, `medium (нужно понимание audience definitions)`, `medium (понимание awareness metrics)`, `medium-high (CFO-friendly framing — но methodology complex)`, `medium-high (требует понимания pause mechanics)`.
- Econ: `low`, `medium`, `medium (two-stage identification = nuanced)`, `trivial`.

Это **free-form strings**, не controlled vocabulary. Studio UI показывает difficulty bar (1-5 stars) → невозможно parse без regex hacking. Также `trivial` = ниже `low`, нет formal scale.

**Impact:** Studio Spec Engine cannot programmatically rank tasks by difficulty (для UI sorting, recommendations).

**Fix:** structured field:
```yaml
ux_hints:
  difficulty_for_manager:
    level: medium      # enum: trivial | low | medium | high
    notes: "Свободный текст что нюансы делают этот уровень."
  difficulty_for_econometrician:
    level: medium
    notes: "..."
```

Apply across 7 YAMLs. Validate enum в task_spec loader (C2 Section 2.1.C `must_have_check`).

### H12 — `mediascope_brandpulse` referenced без Phase A scope clarification

**Где:** reach_planning (`digital_reach_history`), awareness_modeling (`awareness_history` + `competitor_awareness`), brand_to_sales_bridge (`awareness_history`).

**Проблема:** C2 Section 2.1.A 5 adapters list НЕ включает `mediascope_brandpulse` — это «Phase B+ adapter» (per Studio existing Sources table). Но YAMLs reference it as primary source с notes «Phase B+ adapter — не Phase A». Это **half-spec'd dependency**: task profile говорит «нужен BrandPulse», но Studio в Phase A не имеет adapter → user uploads file, Tier 2 LLM fallback пытается parse → unstable.

**Impact:** customer pain point — фарма ICP не может ship awareness/bridge tasks в Phase A reliably (без BrandPulse adapter), хотя YAMLs предполагают workflow.

**Fix:**
1. Add Phase A scope clarification к каждому BrandPulse-referencing field: `phase: B+ (adapter pending Sprint S2 после Phase A); Phase A — Tier 2 LLM fallback OR custom_xlsx wave-based survey`.
2. Update C2 Section 2.1.A note: «BrandPulse adapter — Phase B+ deliverable, не Phase A. Phase A awareness tasks rely on custom_xlsx + Tier 2 LLM».
3. Add field-level `phase_availability` flag для UI to surface «эта source доступна с Phase B+; Phase A — fallback».

### H13 — Cross-task prerequisites не declared в YAML schema

**Где:** scenario_what_if requires output of budget_optimization; brand_to_sales_bridge could be informed by awareness_modeling output.

**Проблема:** prerequisites mentioned только в `ux_hints.common_blockers` — это reactive narrative, не declarative metadata. Studio UI cannot:
- Suggest «complete budget_optimization first» when user opens scenario_what_if.
- Auto-populate trained_model_pickle from previous task в same project.
- Block bundle compose if prerequisite missing.

**Impact:** UX hole — Studio has prerequisite knowledge buried в free text, не usable programmatically.

**Fix:** add top-level `prerequisites` field:
```yaml
prerequisites:
  - app: aurora_optimize
    task: budget_optimization
    artifact_kind: trained_model_pickle
    requirement: required  # required | recommended | optional
    rationale: "Scenario engine needs posterior from prior MMM training."
```

Apply к scenario_what_if (required prerequisite budget_optimization).
Optional prerequisite в brand_to_sales_bridge: awareness_modeling (recommended — иначе Stage 1 awareness extracted from same data, less efficient).

### H14 — Min periods для awareness/bridge не realistic для Russian market BrandPulse cadence

**Где:** awareness_modeling (`awareness_history` min_periods=52 weekly), brand_to_sales_bridge (78 weekly).

**Проблема:** BrandPulse measure ~monthly cadence (12 waves/year). 52 weekly waves требует interpolation (4-5 years calendar для actual measurement basis) ИЛИ 4-5 years monthly waves интерполированных к weekly. Custom XLSX surveys могут быть quarterly (4 waves/year — 13 years!). Real-world Russian fармa клиенты редко имеют:
- 52+ weekly awareness data points actual measurement basis.
- 78+ weekly данные.

Hard min_periods + weekly granularity = **unattainable threshold для большинства клиентов** → quality_gate fails → blocked workflow.

**Impact:** awareness/bridge tasks в Aurora Brand never complete для real customers без Phase B+ BrandPulse subscription (which is costly).

**Fix:** add interpolation acceptance:
- Allow `monthly` granularity для awareness_history (lower min_periods 12 monthly = 52 weeks effective).
- Add `granularity_interpolation` flag: `weekly_via_chow_lin | weekly_via_linear | native_weekly`.
- Quality gate: warning if interpolated > 70% periods, but не block.

Update YAML 2 fields + C2 spec Section 2.1.E quality_gates table.

## 4. Risk register additions

### R9 — YAML schema versioning vs task version

Each YAML has `version: 1.0`, but no migration path for v1 → v2 task profile changes (e.g., adding new must_have field). Studio Spec Engine should:
- Read `version: 1.0`.
- Surface deprecation warnings if user has cached old version.
- Auto-migrate task spec internally (additive fields only).

Phase A: single version (1.0). Phase B+ versioning policy.

### R10 — Trans-language consistency (RU/EN mixed in YAMLs)

YAMLs mix Russian (notes) + English (field names). Some fields use Russian within field id (e.g., proxy task notes mention «бренд» vs «brand»). Consistent style needed:
- Field IDs: snake_case English.
- Notes / descriptions: Russian primary, English supplementary.
- canonical_units / enum values: English.
